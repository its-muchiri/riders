## What "MVP complete" means for this project
Per build-sequencing-roadmap.md, rider.co.ke is second in the build order — it reuses the booking engine from laundry.co.ke but forces real-time dispatch and live-geolocation extensions to be built early. Its MVP is: real-time ride/delivery request, live GPS matching and tracking, M-Pesa payment, and rider onboarding with KYC Tier 1/2 — built on shared modules 1–5 (identity/auth, payments core, booking engine v1, escrow & commission engine v1, KYC pipeline v1). Rider subscription, in-app chat, scheduled bookings, and loyalty points are V2/V3 — don't block DONE on them even though controllers for some already exist.

- Customer can sign up / log in
- Customer can request a trip or delivery by setting pickup and destination points
- System dispatches the request to nearby available riders in proximity order, who can accept within a short window
- Customer sees the rider's live GPS location and ETA once a trip starts (feeds a `trip_pings`-style record per database-schema.md)
- System shows an upfront transparent price estimate before confirmation (distance/time, plus surge if configured)
- Customer pays via M-Pesa STK Push; rider is paid out via escrow, per shared-architecture.md's Escrow & Commission Engine
- An SOS/safety button is visible to both customer and rider and alerts the Dispatcher/Safety Admin with live trip location
- Rider completes onboarding with at least ID + phone verification (KYC Tier 1/2, per shared-architecture.md's trust-tiering table)
- Customer can buy rider safety gear/consumables from the store
- Every image slot (homepage hero, rider profile photos, store product photos for gear/consumables) shows a real, topically relevant photo sourced from Unsplash — not a placeholder box or broken image
- App builds and runs with zero errors, works on mobile width
- Core flow (request → match → live track → pay → review) covered by a smoke test

## Known issues / open questions
- Physical safety and real-time GPS fraud (fake location, route manipulation) are prd.md's stated core risks — the SOS button and the trip location record are the primary mitigations; treat any gap in either as high priority, not a nice-to-have.
- Check open-questions.md for unresolved items (e.g., pre-authorization vs. pay-on-completion) — pick a reasonable default, log it here, and continue.
- Rider onboarding's KYC document fields (src/Views/rider-onboard.php) collect a document reference/URL per document rather than a real file upload — there is no file-storage backend (e.g. Vercel Blob) wired into this project yet. Assumption taken: acceptable for MVP since kyc_documents.file_reference is just a string column and the admin-review step (not yet built) would need a real document viewer regardless; flag for a follow-up pass to wire actual file upload + storage before this goes to real users.
- No admin console exists yet to approve/reject KYC submissions (OnboardingController.submit only creates pending_verification records) — a rider can complete onboarding but has no path to reach status=active. This blocks the full supply-side journey (user-flows.md §2 step 3) and should be the next KYC-adjacent task. During this pass's smoke test, riders were activated with a direct `UPDATE users SET status='active'` against the throwaway test DB to unblock dispatch testing — this is a test-only workaround, not a real approval path.
- Dispatch matching (checklist item 2) is implemented but has no background job/cron: the 30s offer-timeout cascade and "retry once a rider comes online" logic (`Rider\Core\Dispatch::sweepAndCascade`) only run lazily, triggered by something polling (GET /api/v1/trips/{id}, GET /api/v1/riders/me/offers, accept/decline). If nobody is polling a given trip, its dispatch state can go stale until the next poll. Acceptable for MVP without a queue/cron; revisit if this needs to progress with nobody watching (e.g. a scheduled sweep endpoint or real cron).
- Fare rate card (base/per-km/per-min per trip_type, surge trigger/cap) has no stakeholder-approved numbers — open-questions.md only raises the surge-cap question without answering it. Assumption taken (`Rider\Core\Fare`): informal Nairobi boda-boda/taxi-style rates (motorcycle KES 50 base + 15/km + 3/min, car KES 100 base + 40/km + 5/min, parcel KES 60 base + 20/km + 2/min, each with a minimum fare), plus a simple weekday-peak-hours (7-9am, 5-8pm EAT) 1.3x surge capped at 1.5x, always itemized in the estimate response rather than folded silently into the total. Revisit once real commission/pricing numbers are provided.
- ETA in TripController::location is a flat-speed estimate (25 km/h assumed urban average), not a routed/traffic-aware ETA — MAPS_PROVIDER_API_KEY (.env.example) is unconfigured, so no Directions/Distance Matrix API is wired in. Acceptable for MVP; revisit if a Maps provider key is ever provisioned.
- The live tracking map (trip-status.php) uses an unauthenticated OpenStreetMap `openstreetmap.org/export/embed.html` iframe (no API key required) rather than Google Maps, since no Maps provider key is configured. Fine for MVP; OSM's embed widget has no SLA and is meant for light use, so revisit if traffic grows.
- GeocodeController proxies OpenStreetMap Nominatim's public search API server-side (with an identifying User-Agent per its usage policy) to turn the pickup/destination addresses typed in request.php into real coordinates — previously destination_lat/destination_lng were hardcoded to 0 in the request form's JS and pickup fell back to 0 too if the customer didn't click "use my location," which would have made both the new ETA feature and the still-unbuilt fare estimate (item 4) silently wrong. Nominatim is rate-limited (~1 req/s) and meant for light use; fine for MVP traffic, revisit (e.g. a paid geocoder) if volume grows. Local dev note: this requires outbound HTTPS and a working CA bundle — on a Windows PHP install without `curl.cainfo`/`openssl.cafile` set, curl will fail with "SSL certificate problem: unable to get local issuer certificate" and the endpoint fails soft to `{"found": false}` (trip still creates, just at 0,0); not an issue on Vercel's Linux runtime, which has a system CA store.
- Rider trip-status progression (matched → rider_en_route → in_progress → completed) previously had no UI at all — TripController::updateStatus existed but nothing ever called it, and it had no auth guard (any request could move any trip to any status). Both are fixed as part of this pass (see changelog) but flagging here since it was a real, exploitable gap, not just a missing nicety.
- Fixed two pre-existing bugs found during this pass's smoke test: (1) `RiderController::decline` had no `Auth::requireUser` guard (anyone could decline any rider's offer); (2) `RiderController::setAvailability` passed a PHP bool through `PDOStatement::execute()`, which PDO serializes as `''`/`'1'` — MySQL's boolean (tinyint) column rejected `''` for `is_online:false` with "Incorrect integer value". Now binds 0/1 explicitly.

- Local dev note for future passes: this pass found *two* orphaned `php -S 127.0.0.1:8000 -t public` processes still running from earlier sessions (one apparently pointed at a real, long-lived local dev database from a prior pass — registering against it returned unexpectedly high user IDs). Multiple php.exe processes can end up bound to the same Windows port simultaneously without erroring, silently splitting requests between old and new code and producing baffling "route not found" results for routes that definitely exist. Always check `Get-Process php` / `Get-NetTCPConnection -LocalPort <port>` and kill stragglers before trusting a fresh smoke test's results, and tear down your own server process at the end of the pass (this pass did).
